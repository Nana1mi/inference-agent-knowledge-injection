# T2：公开轨迹行为分析

日期：2026-11-10。`[实验]` 在本报告仅指本地数据提取/编码/统计，**没有重跑公开会话的 GPU 实验**。`[论文]` 是外部报告，`[推断]` 是解释或实验建议。

## 数据与可信度

[实验] KernelBench-Hard 两份完整导出共 443 次工具调用，其中31条逐项复核、412条规则初标；InferenceBench 前两 run 的完整压缩序列共 21 个 episode，全部逐项复核。另追加ISO-Bench两份完整导出共58个agent_step，全部逐项复核（见文末），现在共三个来源各两份导出。KernelBench和ISO含可配对原始工具输入/返回，InferenceBench为压缩摘要。样本不是随机抽样，且不同来源的粒度不同，以下不混算。样本 URL、原始行和复核理由均在 [annotations](../data/annotations/)；统计见 [statistics.json](../data/derived/statistics.json)，重建命令 `python scripts/analyze_traces.py`。

KernelBench 是 Claude Opus 4.8 / Claude Code 的两个指定 kernel 任务，初始环境包含参考实现、SOTA入口、测试说明；不是无知识随机探索条件。InferenceBench 样本是 Fable 5.1 Max 的 Scenario A，会话结局标签分别为 failed 和 sglang；后者只是引擎类别，不能等同最终正确性和完整性双门通过。[来源：KernelBench data card/样本 PROMPT；InferenceBench JSON /runs[0:2]]

## 关键案例与失败模式

1. **数据引导跨 kernel 重构。** [实验] KDA #60 的 B 耗时明显高于 A/C，#61–66 的源码编辑预计算 kd/decay；#75 更新分项计时，#79再检查数值与端到端计时。[推断] 这是可借鉴的 profiler → optimizer 接口：提供可定位测量及候选机制，而不规定实现。
2. **评测状态可能被候选污染。** [实验] GEMM #50 odd-K 检查失败，#51–52对比 reduction 开关，#53把进程级开关放进 solution.py 导入路径，#55返回PASS；#58记忆明说会影响 reference。文件保护本身抓不到这类状态修改。[推断] 必须在独立、干净进程生成 oracle；本轮没有独立复现其真实影响，也不判断作弊意图。见 [T6目录](T6_reward_hacking_catalog.md)。
3. **危险经验被保存，但尚未证明被继承。** [实验] 上述 #58是向 memory 写入建议的直接观察；没有下一个会话读取该笔记的证据。[论文] SEIS §5.1 的“接口不许多 token”错误结论传递是作者的独立案例，不能冒充本次 raw trace 标注结果。[SEIS §5.1](https://arxiv.org/html/2610.04646v1#S5.SS1)
4. **轮询是明显可观察活动。** [实验] KDA反复读空日志/未变化文件，并有harness阻止 sleep 的返回。动作数高不证明时间占比高；导出消息时间戳与内嵌 benchmark 时间存在不一致，duration_seconds 全置 null。[论文] Together 真实时间统计在表6：等待57.0%、55.0%、52.7%，不可与我们的动作数拼接。[报告附录C.3，p29](https://www.together.ai/together-compiler-paper)
5. **验证到提交的路径需保护。** [实验] GEMM末尾多次官方计时和PASS可见；KDA末尾亦保留重复计时及PASS。因此这两例不能用来证明“从不验证”。InferenceBench压缩样本中有多次重启与最终存活检查，但没有逐次完整性判决，最终正确性仍不可判定。[推断] selector应保存已验证checkpoint，提交前在清洁环境重验。

## 无证据假设与人类流程对照

[实验] 严格 explicit 假设仅提取到 GEMM 源码注释里的两条，二者可定位到前序数值探针；其余大量工具调用没有可见假设。零条已标 explicit/无证据不能证明 agent 没有无证据假设：分析单位是工具调用、闭源思维不可见，分母过小。**不报告普遍的无证据假设率，也不将 missing 当作“无”。** 数据有误同样需要反证，不凭结果失败判定原始数据错误。

[推断] 按 PLAN 约定的“profile→定位→算子/图→设计”作为目标流程，两个kernel样本的首次实现提前于细分profile，但随后确有测量驱动的改动。它们也多做了构建故障定位和轮询。这里没有匹配的人类工程师轨迹，所以只能做流程对照，不能得出agent比人类更差或更快的经验结论。

## 对框架的映射与知识注入靶点

| 组件 | 可观察缺口 | 建议与证据边界 |
|---|---|---|
| miner | 初始候选先于细分profile，公开harness任务本身限制层次 | [推断] 修改前只问“哪项测量能区分当前候选和替代解释”，不强制先跑NCU |
| profiler | 细分计时与官方端到端计时口径容易分离；轮询多 | [推断] 返回带工作负载/commit/计时定义的证据卡和任务完成事件 |
| optimizer | 数值可行性与性能方向同时变化 | [推断] 技术卡明确前提、适用架构、失败证据和正确性约束 |
| selector | 本样本不足以评判它是否最弱；论文报告最终配置丢失风险 | [推断] 只继承通过独立oracle/完整性门的checkpoint；不能根据此小样本给组件能力排名 |
| accumulation | GEMM把影响reference的开关写入记忆 | [推断] 记忆附测量链接、有效代码版本、可反驳条件；未独立验证者不得写成普遍禁令 |

优先可检验的四个行为改善：修改前提出可区分假设的问题；检索只返回与当前瓶颈匹配的一张卡；对“硬件/接口上限”要求可执行反例探针；继承前自动核查记忆中的结论是否有干净环境证据。它们是后续实验假设，不是本轮已证明的疗效。
